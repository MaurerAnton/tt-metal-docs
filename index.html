1. What Is TT-Metal?

TT-Metal (also called Metalium) is an open-source software development kit (SDK) created by Tenstorrent. It allows programmers to write software that runs on Tenstorrent's custom AI accelerator chips. The repository at github.com/tenstorrent/tt-metal is the single source of truth for all software related to Tenstorrent hardware.

The repo contains two major products:

  1. TT-Metalium — The low-level programming model. Think of it as the "assembly language plus" for Tenstorrent chips. You write kernels in C++ that run directly on the processor's tiny RISC-V CPUs.
  2. TT-NN — The high-level neural network operator library. Think of it as the "PyTorch for Tenstorrent." You write Python code, and TT-NN compiles it into optimized Metalium kernels behind the scenes.

Additionally, the repository includes TT-Train (a training framework), 50+ model implementations, thousands of tests, hardware emulation tools, profilers, and extensive documentation.

3. Tenstorrent Hardware Architecture

Beginner's Note: If you've never programmed an AI accelerator before, think of it like this: Tenstorrent chips are grids of tiny independent processors (called "Tensix cores"), connected by a fast network (NoC). Each core has its own memory (SRAM) and compute units. There is NO cache hierarchy. You explicitly move data around — there is no automatic caching. This means you have full control, but also full responsibility.

3.1. The Chip — A Grid of Specialized Nodes

A Tenstorrent chip (called a Tensix Processor) is a 2D grid of different node types:

NodeSymbolFunction
Tensix CoreTCompute — the main workhorse. Performs matrix/vector operations.
DRAM ControllerDMemory — connects to off-chip DRAM (the "big" memory).
EthernetENetworking — connects to other Tenstorrent chips via standard Ethernet.
ARC / ManagementAControl — ARM RISC-V management processor for chip initialization.
PCIePHost Interface — connects the chip to the host server via PCI Express.

Example Wormhole chip layout: rows and columns of [T, T, T, T, D, T, E, ...] forming a NoC grid. The exact layout varies by chip generation.

3.2. The Tensix Core — Deep Dive

This is the central computational unit. One Tensix core contains:

ComponentCountPurpose
Baby RISC-V CPUs5Control processors — they dispatch instructions, not execute math directly
Matrix Engine (FPU)1Fixed-point / floating-point unit for matrix multiplication and binary operations
Vector Engine (SFPU)1Single instruction FPU for element-wise operations (sin, cos, exp, tanh, etc.)
Packer / Unpacker1 eachConvert between linear memory layout and tiled (32×32) format
NoC Interfaces2Network-on-Chip routers for data movement (NoC0 and NoC1, opposite directions)
SRAM (L1)1.5 MBLocal high-speed memory — stores tiles, intermediate results, circular buffers
Dedicated RegistersMultipleSrcA, SrcB (input), Dst (output), LReg (vector state)

3.3. The Five Baby RISC-V Cores — Who Does What

CoreRoleRuns
Data Movement 0 (DM0 / RISCV_0)ReaderTypically moves data from DRAM into SRAM via NoC0
Data Movement 1 (DM1 / RISCV_1)WriterTypically moves results from SRAM to DRAM via NoC1
UnpackCompute PrepMoves tiles from SRAM into SrcA/SrcB registers for the FPU
MathCompute DispatchIssues instructions to FPU and SFPU (the actual math engines)
PackCompute OutputMoves results from Dst registers back into SRAM circular buffers
Critical insight: The 5 RISC-V cores do NOT do the math themselves. They are dispatch processors. The Unpack core puts data into registers. The Math core tells the FPU/SFPU "multiply these." The Pack core takes the result out. The actual math happens in the hardware engines (FPU and SFPU), which are peripherals controlled by the RISC-V cores.

3.4. Data Flow — The Production Line

DRAM ──NoC0──> [Reader: DM0] ──> CB_in ──> [Unpack] ──> SrcA/SrcB ──> [FPU/SFPU] ──> Dst ──> [Pack] ──> CB_out ──> [Writer: DM1] ──NoC1──> DRAM

This is a software pipeline: while the reader fetches tile N+1, the compute processes tile N, and the writer outputs tile N-1 — all simultaneously, coordinated by circular buffers (CBs) in SRAM.

3.5. Native 32×32 Tile Computing

Unlike GPUs that operate on linear arrays of elements, Tenstorrent hardware natively processes 32×32 element tiles. This means:

  • Tensors are always stored in tiled format on the device. A 48×1024 matrix becomes 64×1024 after padding to the nearest 32-multiple.
  • Tilization (converting linear to tiled) and untilization (reverse) are done on-device by the packer/unpacker hardware at zero host CPU cost.
  • The 32×32 size is optimal for deep learning: it fits key matrix multiply dimensions exactly, keeping SRAM usage low while maximizing compute throughput.

3.6. Memory Model — No Cache Hierarchy

This is the most important architectural difference from CPUs and GPUs:

  • There is NO L1/L2/L3 cache. SRAM is not a cache — it's addressable scratchpad memory.
  • Any Tensix core can read/write the SRAM of any other Tensix core across the chip via NoC.
  • This eliminates cache coherency protocols and provides deterministic, predictable latency.
  • But it means developers must explicitly manage all data movement — there's no "just access the pointer" for off-core data.

4. TT-Metalium — The Low-Level SDK

Analogy: Metalium is to Tenstorrent what CUDA is to NVIDIA or what OpenCL is to GPUs in general. It gives you direct control over the hardware — you allocate buffers, compile kernels, configure circular buffers, and enqueue commands. If TT-NN is "write Python, get results," Metalium is "write C++ kernels that run on individual RISC-V cores."

4.1. The Metalium Programming Flow

Every Metalium program follows this exact sequence:

  1. Open a Device — MeshDevice::create_unit_mesh(device_id)
  2. Get a Command Queue — device->mesh_command_queue(cq_id)
  3. Create a Program — tt::tt_metal::CreateProgram()
  4. Allocate Buffers — MeshBuffer::create(...) for inputs/outputs in DRAM
  5. Transfer Input Data — EnqueueWriteMeshBuffer(cq, buffer, data)
  6. Create Circular Buffers — CreateCircularBuffer(program, core, config) for inter-kernel data
  7. Compile Kernels — CreateKernel(program, "path/to/kernel.cpp", core, config)
  8. Set Runtime Args — SetRuntimeArgs(program, kernel, core, args)
  9. Enqueue and Execute — EnqueueMeshWorkload(cq, workload)
  10. Read Results — EnqueueReadMeshBuffer(cq, output, host_data)

4.2. Three Kernels Per Operation

A typical Metalium operation uses exactly three kernels running on each Tensix core:

KernelRuns OnResponsibilityAPI Include
ReaderDM0 (RISCV_0)Pulls tiles from DRAM into CB_in via NoC0dataflow_api.h
ComputeUnpack + Math + PackPerforms the actual math operation on tilescompute_kernel_api.h
WriterDM1 (RISCV_1)Pushes results from CB_out to DRAM via NoC1dataflow_api.h

4.2.1. Reader Kernel Example

#include <dataflow_api.h>

void kernel_main() {
    const uint32_t a_addr  = get_arg_val<uint32_t>(0);
    const uint32_t b_addr  = get_arg_val<uint32_t>(1);
    const uint32_t n_tiles = get_arg_val<uint32_t>(2);

    constexpr auto cb_in0 = tt::CBIndex::c_0;
    constexpr auto cb_in1 = tt::CBIndex::c_1;
    const uint32_t tile_size_bytes = get_tile_size(cb_in0);

    constexpr auto args_a = TensorAccessorArgs<0>();
    const auto a = TensorAccessor(args_a, a_addr, tile_size_bytes);
    constexpr auto args_b = TensorAccessorArgs<args_a.next_compile_time_args_offset()>();
    const auto b = TensorAccessor(args_b, b_addr, tile_size_bytes);

    for (uint32_t i = 0; i < n_tiles; i++) {
        cb_reserve_back(cb_in0, 1);
        cb_reserve_back(cb_in1, 1);
        const uint32_t cb_in0_addr = get_write_ptr(cb_in0);
        const uint32_t cb_in1_addr = get_write_ptr(cb_in1);
        noc_async_read_tile(i, a, cb_in0_addr);
        noc_async_read_tile(i, b, cb_in1_addr);
        noc_async_read_barrier();  // Wait for NoC reads to complete
        cb_push_back(cb_in0, 1);
        cb_push_back(cb_in1, 1);
    }
}

4.2.2. Compute Kernel Example

#include <compute_kernel_api.h>
#include <compute_kernel_api/common.h>
#include <compute_kernel_api/eltwise_binary.h>

void kernel_main() {
    const uint32_t n_tiles = get_arg_val<uint32_t>(0);
    constexpr auto cb_in0  = tt::CBIndex::c_0;
    constexpr auto cb_in1  = tt::CBIndex::c_1;
    constexpr auto cb_out  = tt::CBIndex::c_16;
    constexpr uint32_t dst_reg = 0;

    binary_op_init_common(cb_in0, cb_in1, cb_out);  // Unpack+Math+Pack
    add_tiles_init(cb_in0, cb_in1, false);           // Unpack+Math

    for (uint32_t i = 0; i < n_tiles; i++) {
        cb_wait_front(cb_in0, 1);          // Unpack: wait for data
        cb_wait_front(cb_in1, 1);          // Unpack: wait for data
        tile_regs_acquire();               // Math: lock Dst register
        add_tiles(cb_in0, cb_in1, 0, 0, dst_reg);  // Unpack+Math: DO THE ADD
        tile_regs_commit();                // Math: unlock Dst register
        cb_pop_front(cb_in0, 1);           // Unpack: free input
        cb_pop_front(cb_in1, 1);           // Unpack: free input
        cb_reserve_back(cb_out, 1);        // Pack: reserve output space
        tile_regs_wait();                  // Pack: wait for Dst ready
        pack_tile(dst_reg, cb_out, 0);     // Pack: write result to CB
        tile_regs_release();               // Pack: release Dst
        cb_push_back(cb_out, 1);           // Pack: signal output ready
    }
}

4.2.3. Writer Kernel Example

#include <dataflow_api.h>

void kernel_main() {
    const uint32_t c_addr  = get_arg_val<uint32_t>(0);
    const uint32_t n_tiles = get_arg_val<uint32_t>(1);
    constexpr auto cb_out = tt::CBIndex::c_16;
    const uint32_t tile_size_bytes = get_tile_size(cb_out);

    constexpr auto args_c = TensorAccessorArgs<0>();
    const auto c = TensorAccessor(args_c, c_addr, tile_size_bytes);

    for (uint32_t i = 0; i < n_tiles; i++) {
        cb_wait_front(cb_out, 1);
        const uint32_t cb_out_addr = get_read_ptr(cb_out);
        noc_async_write_tile(i, c, cb_out_addr);
        noc_async_write_barrier();
        cb_pop_front(cb_out, 1);
    }
}

4.3. Circular Buffers — The Synchronization Mechanism

Circular buffers are ring buffers in SRAM that coordinate data flow between kernels:

  • Reader writes tiles into cb_in0 and calls cb_push_back
  • Compute waits on cb_wait_front, processes, writes to cb_out via cb_push_back
  • Writer waits on cb_wait_front(cb_out), then writes to DRAM and calls cb_pop_front
  • Each CB typically holds 2+ tiles — enabling pipelining: reader fetches tile 2 while compute processes tile 1

This is a hardware-backed producer-consumer mechanism. The RISC-V cores use hardware mutex and metadata synchronization — no software spinlocks needed.

4.4. Compute API — Hardware Abstraction

The Compute API solves the problem of different hardware generations having different vector widths and instruction sets. When you call add_tiles(...) or sin_tile(...), the compiler selects the correct implementation for your target chip:

  • Grayskull: 64-element vectors, 19-bit FP, 4 iterations for sine
  • Wormhole: 32-element vectors, 32-bit FP, 8 iterations for sine
  • Blackhole: 32-element vectors, 32-bit FP, 8 iterations (with float_to_int16 optimization)

4.5. SPMD — Single Program, Multiple Data

Metalium supports the SPMD model: all Tensix cores run the same kernel code but on different data slices. There is no built-in threadIdx or get_global_id(). Instead, you explicitly pass different runtime arguments to each core:

auto [num_cores, all_cores, core_group_1, core_group_2,
      num_tiles_per_core_group_1, num_tiles_per_core_group_2]
    = tt::tt_metal::split_work_to_cores(grid_size, work_size);

for (const auto& core : all_cores) {
    SetRuntimeArgs(program, reader, core, {a_addr, b_addr, work_per_core, core_id});
    SetRuntimeArgs(program, compute, core, {work_per_core});
    SetRuntimeArgs(program, writer, core, {c_addr, work_per_core, core_id});
}

14. Glossary — Every Term Explained

TermDefinition
ARCARM RISC-V management processor on the chip — handles initialization, reset, and system management
Baby RISC-VThe 5 small RISC-V CPUs inside each Tensix core. They are 32-bit RV32IM processors (no floating-point unit). They dispatch instructions to hardware engines rather than doing computation themselves.
Blackhole (BH)The latest Tenstorrent chip generation (2025+). 32-element vector units, enhanced performance vs Wormhole.
bfloat16 (bf16)Brain Floating Point 16-bit format — same exponent range as fp32 but reduced mantissa precision. Used extensively in Tenstorrent operations.
CB (Circular Buffer)A ring buffer in SRAM that acts as a producer-consumer queue between kernels. Hardware-synchronized via metadata.
CB IndexNumeric identifier for a circular buffer (c_0 through c_31). Each CB must have a unique index on a Tensix core.
Command QueueA FIFO queue of commands (buffer writes, kernel launches, buffer reads) that the device executes asynchronously. Two queues per device: queue 0 (compute), queue 1 (data).
Compute APIAn abstraction layer that lets the same kernel code run on different hardware generations. The compiler selects the right microcode for the target chip.
CoreCoordA 2D coordinate {x, y} identifying a specific Tensix core on the chip grid.
CoreGridThe set of all available Tensix cores on a device, represented as a CoreRange.
CoreRangeA rectangular range of cores from {start.x, start.y} to {end.x, end.y}.
DataFormatEnum specifying the numeric format of tile data: Float32, Float16, Float16_b (bfloat16), Int32, UInt16, etc.
DM0 / DM1Data Movement RISC-V cores 0 and 1. DM0 typically handles reads (NoC0), DM1 handles writes (NoC1).
DP (Data Parallel)Parallelization strategy: each device processes a different batch of data, same model weights.
DRAMOff-chip memory (8-48 GB per chip). Accessed via DRAM controllers on the chip grid. Much larger than SRAM but higher latency.
Dst RegisterDestination register bank — holds FPU/SFPU computation results. 8 Dst registers per Tensix core.
Ethernet (ETH)Standard Ethernet links used for inter-chip communication. Supports up to 800 Gbps on Wormhole/Blackhole.
Fast DispatchAsynchronous command processing using dedicated RISC-V cores on the device. The default and recommended mode.
FPUFixed/Floating-Point Unit — the matrix engine in a Tensix core. Performs matrix multiplications, element-wise binary operations (add, mul).
GalaxyA 32-chip Wormhole system (4x QuietBox equivalent). Used for largest single-host models.
Grayskull (GS)First-generation Tenstorrent chip. 64-element vectors, 19-bit floating point. Legacy generation.
HAL (Hardware Abstraction Layer)The layer that translates Metalium API calls into chip-specific register writes. Different HAL implementations for Grayskull, Wormhole, Blackhole.
Interleaved BufferDefault memory layout: data is distributed evenly across all DRAM controllers. Best for general workloads.
L1Another name for the 1.5 MB SRAM inside each Tensix core. Not a cache — it's addressable scratchpad memory.
LLK (Low Level Kernels)The tt-llk library (69,353 lines of C++) containing hardware-intrinsic-level kernel code for each processor generation.
LRegLocal Register — holds internal state of the SFPU during vector computations.
Math CoreThe middle RISC-V CPU in the compute pipeline. Dispatches instructions to FPU and SFPU.
MeshA collection of Tenstorrent devices treated as a unified computational unit. A single chip is a 1x1 mesh.
MeshDeviceC++ class representing a mesh of devices. All operations go through a MeshDevice.
MeshWorkloadA collection of Programs to execute on a mesh, with per-submesh coordinate ranges.
MetaliumThe low-level SDK for Tenstorrent hardware. Also called tt-metal, Metal, TT-Metalium.
MPMDMultiple Program Multiple Data — different Tensix cores run different kernel programs. Used for specialized patterns like multicast matmul.
n150 / n300Wormhole products: n150 = 1 chip, n300 = 2 chips on one board (L-chip + R-chip)
NoCNetwork-on-Chip — the 2D torus interconnect that connects all nodes on the chip. Two independent NoCs (NoC0 and NoC1) running in opposite directions.
p100 / p150Blackhole products: p100 = 1 chip, p150 = 1 chip (different SKU)
Pack / UnpackHardware engines that convert between linear memory format and 32×32 tiled format. The Pack core controls the packer; the Unpack core controls the unpacker.
ProgramA Metalium object containing kernels, circular buffers, and runtime arguments for a specific computation. Analogous to a CUDA kernel launch configuration.
QuietBoxAn 8-chip system (8×Wormhole or 4×Blackhole) in a mesh topology. The standard multi-chip configuration.
Runtime ArgsArguments passed to kernels at runtime (vs compile-time args). Set per-core via SetRuntimeArgs().
SFPUSingle-instruction FPU — the vector engine. Performs element-wise operations on 32-element vectors: sin, cos, exp, tanh, relu, etc.
Sharded BufferMemory layout where tensor data is distributed across multiple Tensix cores' SRAM based on physical topology. Reduces NoC traffic.
Slow DispatchDebug mode where host CPU manages every device operation synchronously. Set via TT_METAL_SLOW_DISPATCH_MODE=1.
SPMDSingle Program Multiple Data — all Tensix cores run the same kernel but on different data slices. The default Metalium model.
SrcA / SrcBSource register banks — hold input data for the FPU matrix engine.
SRAMStatic RAM inside each Tensix core (1.5 MB per core). Fast, deterministic access. Not a cache — addressable scratchpad.
Tensix CoreThe basic compute unit: 5 Baby RISC-V CPUs + FPU + SFPU + Pack/Unpack + 1.5MB SRAM + 2 NoC interfaces.
Tensix ProcessorThe entire chip — a grid of Tensix cores plus DRAM controllers, Ethernet links, ARC, and PCIe.
TileA 32×32 matrix of elements in a specific data format. The native computational unit of Tenstorrent hardware.
TP (Tensor Parallel)Parallelization strategy: model weights are split across multiple devices (each holds part of each layer).
tt-FabricThe inter-host communication fabric that routes traffic between multiple 32-chip boxes over Ethernet.
TTFTTime To First Token — milliseconds to generate the first output token in LLM inference.
T/S/UTokens per Second per User — throughput of token generation per user after prefill. 1 / inter-token latency.
Wormhole (WH)Second-generation Tenstorrent chip. 32-element vector units, 32-bit FP, 800G Ethernet. Current mainstream generation.

15.2. Recommended Bounty Hunting Strategy

  1. Start with circular buffers — relatively small surface (15K lines), well-defined boundaries, every operation uses them, bugs here affect everything.
  2. Focus on edge cases in operators — zero-size tensors, NaN/Inf propagation, format boundary conditions.
  3. Multi-chip distributed code — very low competition, complex race conditions possible.
  4. Build a fuzzing harness targeting tile-level operations with random tensor shapes, formats, and sharding configurations.
