1. What Is TT-Metal?

111| 112|

113|TT-Metal (also called Metalium) is an open-source software development kit (SDK) created by Tenstorrent. It allows programmers to write software that runs on Tenstorrent's custom AI accelerator chips. The repository at github.com/tenstorrent/tt-metal is the single source of truth for all software related to Tenstorrent hardware. 114|

115| 116|

The repo contains two major products:

117|
    118|
  1. TT-Metalium — The low-level programming model. Think of it as the "assembly language plus" for Tenstorrent chips. You write kernels in C++ that run directly on the processor's tiny RISC-V CPUs.
    2. 119|
  2. TT-NN — The high-level neural network operator library. Think of it as the "PyTorch for Tenstorrent." You write Python code, and TT-NN compiles it into optimized Metalium kernels behind the scenes.
    3. 120|
121| 122|

Additionally, the repository includes TT-Train (a training framework), 50+ model implementations, thousands of tests, hardware emulation tools, profilers, and extensive documentation.

3.7. Software-Only Emulation: tt-emule

No hardware? No problem. tt-emule lets you run tt-metal kernel and host code on a standard x86-64 Linux machine — zero Tenstorrent hardware, drivers, or firmware required. It emulates SRAM, DRAM, circular buffers, and NoC operations in software.

What it emulates:

  • Core L1 SRAM (1-4 MB) and DRAM banks with proper NoC address routing
  • Circular buffers with synchronization (mutex+condvar)
  • Data-movement and compute threads as OS threads
  • NoC async read/write, remote semaphores, runtime args

What it does NOT emulate:

  • Real RISC-V ISA or cycle-accurate timing
  • Actual async NoC (all DMA is synchronous in emulation)
  • Ethernet/dispatch fabric or UMD layers
  • Real tile layout conversions (tilize/untilize are identity copies)

Setup: Clone tt-emule as sibling to tt-metal:

git clone https://github.com/tenstorrent/tt-emule.git ../tt-emule

cd tt-metal
cmake -S . -B build_emule -G Ninja \
  -DCMAKE_TOOLCHAIN_FILE=cmake/x86_64-linux-clang-20-libstdcpp-toolchain.cmake \
  -DCMAKE_BUILD_TYPE=Release \
  -DTT_METAL_USE_EMULE=ON -DTT_EMULE_PATH=../tt-emule \
  -DWITH_PYTHON_BINDINGS=ON -DTT_METAL_BUILD_TESTS=ON -DTTNN_BUILD_TESTS=ON \
  -DENABLE_TRACY=OFF -DENABLE_DISTRIBUTED=ON
cmake --build build_emule -j$(nproc)

Run with emulation:

export TT_METAL_EMULE_MODE=1
export TT_METAL_SLOW_DISPATCH_MODE=1
export TT_METAL_MOCK_CLUSTER_DESC_PATH=/path/to/wormhole_N150.yaml

3. Tenstorrent Hardware Architecture

197| 198|
199| Beginner's Note: If you've never programmed an AI accelerator before, think of it like this: Tenstorrent chips are grids of tiny independent processors (called "Tensix cores"), connected by a fast network (NoC). Each core has its own memory (SRAM) and compute units. There is NO cache hierarchy. You explicitly move data around — there is no automatic caching. This means you have full control, but also full responsibility. 200|
201| 202|

3.1. The Chip — A Grid of Specialized Nodes

203|

A Tenstorrent chip (called a Tensix Processor) is a 2D grid of different node types:

204| 205| 206| 207| 208| 209| 210| 211|
NodeSymbolFunction
Tensix CoreTCompute — the main workhorse. Performs matrix/vector operations.
DRAM ControllerDMemory — connects to off-chip DRAM (the "big" memory).
EthernetENetworking — connects to other Tenstorrent chips via standard Ethernet.
ARC / ManagementAControl — ARM RISC-V management processor for chip initialization.
PCIePHost Interface — connects the chip to the host server via PCI Express.
212| 213|

Example Wormhole chip layout: rows and columns of [T, T, T, T, D, T, E, ...] forming a NoC grid. The exact layout varies by chip generation.

3.2. The Tensix Core — Deep Dive

216|

This is the central computational unit. One Tensix core contains:

217| 218| 219| 220| 221| 222| 223| 224| 225| 226|

Matrix Engine (FPU)1Fixed-point / floating-point unit for matrix multiplication and binary operations

3.3. The Five Baby RISC-V Cores — Who Does What

229| 230| 231| 232| 233| 234| 235| 236|
CoreRoleRuns
Data Movement 0 (DM0 / RISCV_0)ReaderTypically moves data from DRAM into SRAM via NoC0
Data Movement 1 (DM1 / RISCV_1)WriterTypically moves results from SRAM to DRAM via NoC1
UnpackCompute PrepMoves tiles from SRAM into SrcA/SrcB registers for the FPU
MathCompute DispatchIssues instructions to FPU and SFPU (the actual math engines)
PackCompute OutputMoves results from Dst registers back into SRAM circular buffers
237| 238|
239| Critical insight: The 5 RISC-V cores do NOT do the math themselves. They are dispatch processors. The Unpack core puts data into registers. The Math core tells the FPU/SFPU "multiply these." The Pack core takes the result out. The actual math happens in the hardware engines (FPU and SFPU), which are peripherals controlled by the RISC-V cores. 240|
241| 242|

3.4. Data Flow — The Production Line

243|
DRAM ──NoC0──> [Reader: DM0] ──> CB_in ──> [Unpack] ──> SrcA/SrcB ──> [FPU/SFPU] ──> Dst ──> [Pack] ──> CB_out ──> [Writer: DM1] ──NoC1──> DRAM
244| 245|

This is a software pipeline: while the reader fetches tile N+1, the compute processes tile N, and the writer outputs tile N-1 — all simultaneously, coordinated by circular buffers (CBs) in SRAM.

3.5. Native 32×32 Tile Computing

248|

Unlike GPUs that operate on linear arrays of elements, Tenstorrent hardware natively processes 32×32 element tiles. This means:

249|
    250|
  • Tensors are always stored in tiled format on the device. A 48×1024 matrix becomes 64×1024 after padding to the nearest 32-multiple.
    • 251|
  • Tilization (converting linear to tiled) and untilization (reverse) are done on-device by the packer/unpacker hardware at zero host CPU cost.
    • 252|
  • The 32×32 size is optimal for deep learning: it fits key matrix multiply dimensions exactly, keeping SRAM usage low while maximizing compute throughput.
    • 253|
254| 255|

3.6. Memory Model — No Cache Hierarchy

256|

This is the most important architectural difference from CPUs and GPUs:

257|
    258|
  • There is NO L1/L2/L3 cache. SRAM is not a cache — it's addressable scratchpad memory.
    • 259|
  • Any Tensix core can read/write the SRAM of any other Tensix core across the chip via NoC.
    • 260|
  • This eliminates cache coherency protocols and provides deterministic, predictable latency.
    • 261|
  • But it means developers must explicitly manage all data movement — there's no "just access the pointer" for off-core data.
    • 262|

3.9. Sub-Devices — Partitioning a Chip

You can partition one physical chip into multiple independent sub-devices, each with its own set of Tensix cores. This allows running multiple independent workloads simultaneously on one chip, isolating experiments (one sub-device crash doesn't affect others), and resource partitioning in multi-tenant environments.

Each sub-device gets a rectangular range of cores (CoreRange) and operates as if it were an independent device. Sub-devices within the same chip share DRAM bandwidth and NoC resources — performance isolation is partial. See the "Sub-Devices" tech report in tech_reports/ for the full API.

4.7. Buying Guide: Which Card Should You Get?

For learning / development / hobby:

n150s ($999) — cheapest entry point. Passive cooling. Good for learning TT-Metal, developing operators, running small models (Llama 3.2 1B/3B). No multi-chip scaling.

For LLM inference (7B-11B models):

n300 ($1,399) — dual Wormhole. Runs Llama 3.1 8B at 832 T/s, Qwen 2.5 7B at 707 T/s. 24 GB memory. Best value for 7B-class inference.

For maximum single-card performance:

p150a ($1,399) — Blackhole. 120 cores, 32 GB, 512 GB/s BW, ~142 TFLOPS BF16. ~2x faster than n150. Best single-card option.

For large models (70B+):

Single cards insufficient. Need QuietBox (8-chip, ~$8,000+) or Galaxy (32-chip). Contact Tenstorrent enterprise sales.

Active vs. passive cooling:

  • Active (d/a suffix): Built-in fan. Louder but self-contained. Good for desktop/workstation.
  • Passive (s/b suffix): Heatsink only. Requires server chassis airflow. Quieter but needs proper cooling.

For a desktop PC: get active cooling (n150d, p150a). For a server rack with high-RPM fans: passive is fine.

Do you need QSFP-DD cables?

Only if connecting multiple cards for multi-chip scaling. Single card: no cables needed. Two n150 cards cannot be linked — buy an n300 instead. Two p150 cards can link via QSFP-DD 800G cables ($200/0.5m) for 2-chip mesh.

4. TT-Metalium — The Low-Level SDK

285| 286|
287| Analogy: Metalium is to Tenstorrent what CUDA is to NVIDIA or what OpenCL is to GPUs in general. It gives you direct control over the hardware — you allocate buffers, compile kernels, configure circular buffers, and enqueue commands. If TT-NN is "write Python, get results," Metalium is "write C++ kernels that run on individual RISC-V cores." 288|

4.1. The Metalium Programming Flow

291|

  2. Get a Command Queue — device->mesh_command_queue(cq_id)
    3. 295|
  3. Create a Program — tt::tt_metal::CreateProgram()

4.3. Circular Buffers — The Synchronization Mechanism

397|

Circular buffers are ring buffers in SRAM that coordinate data flow between kernels:

398|
    399|
  • Reader writes tiles into cb_in0 and calls cb_push_back
    • 400|
  • Compute waits on cb_wait_front, processes, writes to cb_out via cb_push_back
    • 401|
  • Writer waits on cb_wait_front(cb_out), then writes to DRAM and calls cb_pop_front
    • 402|
  • Each CB typically holds 2+ tiles — enabling pipelining: reader fetches tile 2 while compute processes tile 1
    • 403|
404|

This is a hardware-backed producer-consumer mechanism. The RISC-V cores use hardware mutex and metadata synchronization — no software spinlocks needed.

4.6. MPMD — Multiple Program Multiple Data

While SPMD runs the same kernel on all cores with different args, MPMD runs different kernels on different cores. This is used for specialized patterns:

Use CaseWhy MPMD
Multicast matmulOne core broadcasts weights to many compute cores — reader kernel differs from compute kernels
Pipeline stagesDifferent pipeline stages run on different physical cores — e.g., pre-processing on core (0,0), compute on (0,1)-(7,7), post-processing on (7,7)
Heterogeneous gridEdge cores handle I/O, interior cores handle compute — different kernels for different positions
Collective communicationAll-reduce, scatter, gather need different logic on root vs. worker cores

MPMD is configured by compiling different kernels for different core ranges:

// Reader kernel for all cores
auto reader = CreateKernel(program, "reader.cpp", all_cores,
    DataMovementConfig{.processor = DataMovementProcessor::RISCV_0});

// Default compute kernel for most cores
auto compute = CreateKernel(program, "compute.cpp", core_group_1, ComputeConfig{});

// Special compute kernel for edge cores
auto compute_edge = CreateKernel(program, "compute_edge.cpp", core_group_2, ComputeConfig{});
Most users never need MPMD. SPMD is the default and sufficient for 95% of workloads. MPMD is for performance-critical patterns where asymmetric core roles provide measurable benefit.

5. End-to-End Programming: Your First TT-Metal Program

5.1. Complete Host Program (Python via TT-NN)

This is the simplest complete program: add two tensors on-device and read back the result.

import torch
import ttnn

# 1. Initialize device
device = ttnn.open_device(device_id=0)

# 2. Create input data on host
torch_a = torch.rand((1, 1, 32, 32), dtype=torch.bfloat16)
torch_b = torch.rand((1, 1, 32, 32), dtype=torch.bfloat16)

# 3. Move tensors to device (tile-aligned: 32×32)
tt_a = ttnn.from_torch(torch_a, dtype=ttnn.bfloat16, layout=ttnn.TILE_LAYOUT, device=device)
tt_b = ttnn.from_torch(torch_b, dtype=ttnn.bfloat16, layout=ttnn.TILE_LAYOUT, device=device)

# 4. Run operation on device
tt_c = ttnn.add(tt_a, tt_b)

# 5. Read result back to host
torch_c = ttnn.to_torch(tt_c)
print(f"Result matches: {torch.allclose(torch_c, torch_a + torch_b)}")

# 6. Close device
ttnn.close_device(device)

#include "tt_metal/api/tt-metalium/device.hpp"
#include "tt_metal/api/tt-metalium/buffer.hpp"
#include "tt_metal/api/tt-metalium/mesh_device.hpp"

int main() {
    // 1. Open device
    auto mesh = tt::tt_metal::MeshDevice::create_unit_mesh(0);
    auto& device = *mesh;
    auto& cq = device.mesh_command_queue(0);

    // 2. Allocate input/output buffers in DRAM
    constexpr uint32_t size = 32 * 32 * 2;  // 32x32 bfloat16
    auto buf_a = tt::tt_metal::MeshBuffer::create(
        mesh, size, tt::tt_metal::BufferType::DRAM, tt::tt_metal::TensorMemoryLayout::INTERLEAVED);
    auto buf_b = tt::tt_metal::MeshBuffer::create(
        mesh, size, tt::tt_metal::BufferType::DRAM, tt::tt_metal::TensorMemoryLayout::INTERLEAVED);
    auto buf_c = tt::tt_metal::MeshBuffer::create(
        mesh, size, tt::tt_metal::BufferType::DRAM, tt::tt_metal::TensorMemoryLayout::INTERLEAVED);

    // 3. Write input data to device
    std::vector<uint16_t> data_a(size/2, 0x3F80);  // bf16(1.0)
    std::vector<uint16_t> data_b(size/2, 0x4000);  // bf16(2.0)
    cq.enqueue_write_buffer(buf_a, data_a.data(), false);
    cq.enqueue_write_buffer(buf_b, data_b.data(), false);

    // 4. Create program
    auto program = tt::tt_metal::CreateProgram();

    // 5. Create circular buffers (same CB indices as kernel expects)
    auto cb_config = tt::tt_metal::CircularBufferConfig(size, {{tt::CBIndex::c_0, tt::DataFormat::Float16_b}});
    auto cb0 = tt::tt_metal::CreateCircularBuffer(program, core, cb_config);
    // ... cb1, cb_out similarly

    // 6. Compile kernels
    auto reader_kernel = tt::tt_metal::CreateKernel(
        program, "kernels/reader.cpp", core,
        tt::tt_metal::DataMovementConfig{.processor = tt::tt_metal::DataMovementProcessor::RISCV_0});
    auto compute_kernel = tt::tt_metal::CreateKernel(
        program, "kernels/compute.cpp", core,
        tt::tt_metal::ComputeConfig{});
    auto writer_kernel = tt::tt_metal::CreateKernel(
        program, "kernels/writer.cpp", core,
        tt::tt_metal::DataMovementConfig{.processor = tt::tt_metal::DataMovementProcessor::RISCV_1});

    // 7. Set runtime args
    const std::vector<uint32_t> reader_args = {buf_a->address(), buf_b->address(), /*n_tiles=*/1};
    tt::tt_metal::SetRuntimeArgs(program, reader_kernel, core, reader_args);

    // 8. Enqueue and execute
    tt::tt_metal::EnqueueMeshWorkload(cq, {program}, false);

    // 9. Read results
    std::vector<uint16_t> result(size/2);
    cq.enqueue_read_buffer(buf_c, result.data(), true);

5.5. PyTorch Interoperability

TT-NN is designed to work alongside PyTorch. You can freely mix them:

import torch
import ttnn

device = ttnn.open_device(0)

# Torch -> TT: send tensor to device
torch_in = torch.randn((1, 1, 32, 256), dtype=torch.bfloat16)
tt_tensor = ttnn.from_torch(torch_in, dtype=ttnn.bfloat16, layout=ttnn.TILE_LAYOUT, device=device)

# Run TT operation
tt_result = ttnn.gelu(tt_tensor)

# TT -> Torch: bring result back
torch_out = ttnn.to_torch(tt_result)

# Continue with PyTorch on CPU/GPU
final = torch.nn.functional.softmax(torch_out, dim=-1)

ttnn.close_device(device)
Model compatibility check: Not all PyTorch ops have TT-NN equivalents. Check tenstorrent.com/developers for the model compatibility matrix. Standard transformer ops (matmul, softmax, layer_norm, gelu, attention) are well-supported. Exotic ops (custom CUDA kernels, sparse ops, dynamic shapes) likely need porting.

Memory layout awareness

  • ROW_MAJOR_LAYOUT: Linear memory (standard PyTorch). Used for host tensors and untilized device data.
  • TILE_LAYOUT: 32x32 tiled format. Required for most TT-NN operations. from_torch converts automatically.
  • Padding: Non-32-aligned dimensions are auto-padded. A 48x1024 matrix becomes 64x1024 on device.
  • from_torch with ROW_MAJOR: Use only for data you need in linear format (e.g., embeddings). Most compute ops require TILE_LAYOUT.

5.7. Common Operational Questions

Do I need root to run programs?

No. Normal TT-Metal programs (inference, model demos, development) run as a regular user. Root is only needed for one-time setup: install_dependencies.sh, hugepages, IOMMU configuration, CPU governor. Device access goes through /dev/tenstorrent managed by TT-KMD.

Can multiple processes share one device?

No. ttnn.open_device(0) takes exclusive ownership. One process = one device at a time. Multiple processes can use different devices (different device_id). For multi-device setups, use MeshDevice to manage multiple chips as one logical unit.

What happens if my model is too big?

Memory allocation fails with a clear error. No silent OOM or swapping — SRAM and DRAM are explicitly allocated. Solutions: reduce batch size, use shorter context, enable BFP4 quantization, or move to a device with more memory.

How fast is host-to-device transfer?

GenerationPCIeTheoreticalPractical Sustained
Wormhole (n150/n300)4.0 x16~31.5 GB/s~25-28 GB/s
Blackhole (p100/p150)5.0 x16~63 GB/s~50-56 GB/s

Inter-chip bandwidth (QSFP-DD): up to 800 Gbps (100 GB/s). On Galaxy, only 4 of 32 chips have high-bandwidth PCIe; use those for host I/O.

6.2. Training Workflow

TT-Train provides autograd, optimizers, and training loop infrastructure. A typical training script:

  1. Load model: Using TT-NN or TT-Forge to place the model on device(s)
  2. Forward pass: Data flows through TT-NN operations — all compute on Tenstorrent hardware
  3. Loss computation: Use TT-NN loss ops (cross_entropy, mse, etc.)
  4. Backward pass: TT-Train autograd traces the forward graph and produces gradients
  5. Optimizer step: Apply gradients via optimizers (SGD, Adam, etc.)
  6. Data loading: Host CPU feeds data via PCIe. Keep pipeline full with async transfers (command queue 1)
Training is less mature than inference. TT-Train has 111K lines (vs 541K for TT-NN + 529K for Metalium). Fewer models have been validated for training. For production training, also evaluate TT-Blacksmith (40+ training recipes) and TT-Forge (800+ tested models). 8.5. How to Port a New Model to TT-Metal

There is no single "porting wizard," but the general workflow is well-established:

  1. Check compatibility first. Visit tenstorrent.com/developers — the model compatibility matrix shows which models are tested. Standard transformer architectures (Llama, Qwen, Mistral, Phi, BERT) port cleanly. Vision models (ResNet, ViT, SD) are supported. Exotic ops (custom CUDA kernels, sparse attention, dynamic control flow) need custom kernel development.
  2. Start in Python with TT-NN. Write your model using ttnn.matmul(), ttnn.softmax(), ttnn.layer_norm(), ttnn.gelu(), etc. Run with small tensors (1x1x32x32) on a single core first. Use BF16 (HiFi4) precision for correctness.
  3. Place in the right directory. Production-ready models go in models/demos/. Experimental/bring-up models go in models/experimental/. Follow the existing directory conventions (each model gets its own directory with demo scripts, test configs, and weight handling).
  4. Handle weights. Most models load HuggingFace safetensors via the tt_transformers weight loader. Set HF_MODEL=org/model and the first run auto-caches TTNN tensors. For custom formats, write a weight conversion script (see existing examples in models/demos/*/scripts/).
  5. Verify correctness. Compare outputs against PyTorch reference at BF16 precision, tile by tile. Use ttnn.to_torch() to pull results back and torch.allclose() to compare. Tolerance: ~1e-2 for BF16, ~1e-1 for BFP8.
  6. Profile and optimize. Enable the device profiler, check math utilization and CB stalls. Apply quantization (bfp8 for MLP layers, keep BF16 for attention). Use the Tracy profiler for timeline analysis.
  7. Scale up. Start 1 core → all cores on 1 chip → multi-chip (n300, T3K, Galaxy). Use split_work_to_cores() for SPMD distribution. Write a pytest demo following existing conventions.
Check existing models for reference. The tt_transformers demo supports 40+ LLMs with a single entry point — study how new models are added there. For missing ops, you may need to write custom Metalium kernels (see Op Kernel Development tech report).

8.6. Flash Attention (SDPA)

TT-NN provides an optimized scaled_dot_product_attention implementation in the transformer operation category. This is the standard attention mechanism used by all LLM demos.

# The SDPA op is used internally by tt_transformers — you typically don't call it directly.
# It's configured via precision settings:
# sdpa_decode: hifi2na  (no accumulation, fast for token-by-token generation)
# sdpa_prefill: hifi4   (BF16, reference accuracy for prompt processing)
Attention precision matters critically. Use BF16 (HiFi4) for attention, softmax, and layer_norm. BFP8 (HiFi2) has minor degradation — acceptable for GEMM. BFP4 (LoFi) produces garbage for attention — never use it. SDPA is the most precision-sensitive operation in any transformer model.

Tech report: "Flash Attention" in tech_reports/ — optimized attention implementation on Wormhole with detailed performance analysis.

8.7. Collective Communication (CCL) for Multi-Chip

TT-NN's ccl operation category provides distributed communication primitives: all_gather, reduce_scatter, all_reduce. These are essential for tensor parallelism (TP) and data parallelism (DP) across multiple chips.

OperationWhat It DoesUsed In
all_gatherEach chip broadcasts its shard to all others — every chip gets the full tensorGathering results after distributed compute
reduce_scatterEach chip reduces its shard and scatters the result — each chip gets a different portionDistributing gradients in DP training
all_reduceReduce + broadcast — every chip gets the same reduced resultSyncing gradients across all chips

Scaling patterns:

  • TP (Tensor Parallel): Model weights split across chips. Each chip holds part of each layer. CCL ops synchronize activations between layers. Used by Llama 70B at TP=8 (8 chips).
  • DP (Data Parallel): Each chip processes a different batch with full model copy. CCL ops sync gradients after backward pass. Used by Falcon 7B at DP=32 (32 chips, 13,517 T/S).
  • Hybrid TP+DP: Combine both for large-scale training — TP within a node, DP across nodes.

Multi-host (tt-Fabric):

For systems spanning multiple host servers, tt-Fabric routes traffic between 32-chip boxes over standard Ethernet (up to 800 Gbps). The DeepSeek-V3 demo runs on 2× Galaxy (64 chips across 2 hosts):

./models/demos/deepseek_v3/scripts/launch_multihost_galaxy.py 2x -- \\
  python models/demos/deepseek_v3/demo/demo.py --model-path $DEEPSEEK_V3_HF_MODEL

Build with distributed support (default): OpenMPI required. Tech reports: "TT-Fabric Architecture," "TT-Distributed Architecture," "Programming Mesh of Devices," "Programming Multiple Meshes."

10.2. Graph Capture & Execution Replay

Graph capture lets you record a sequence of operations and replay them as a single optimized program — avoiding per-op dispatch overhead.

How it works:

  1. Start capture: Begin recording TT-NN operations
  2. Run model: Execute your model once — all ops are traced into a graph
  3. Stop capture: The graph is compiled into an optimized Metalium program
  4. Replay: Subsequent runs execute the compiled graph directly — no per-op Python/C++ overhead

Key benefits:

  • Latency reduction: Typical 10-30% improvement for repeated inference — eliminates dispatch overhead
  • Memory optimization: Compiler can fuse operations, eliminate intermediate buffers, optimize CB sizes
  • Production serving: Used by Stable Diffusion (--with_trace flag) and the vLLM TT Plugin

Where to find it:

  • TT-NN C++ API: graph_tracking.hpp — core graph capture infrastructure
  • TT-NN Python: ttnn.begin_trace_capture() / ttnn.end_trace_capture()
  • Model demos that use it: Stable Diffusion XL (--with_trace flag), LLM demos
  • Compiler stack: TT-MLIR and TT-Forge use graph capture internally for AOT compilation

11.7. Pipeline Parallelism (PP)

In addition to TP (Tensor Parallel — split weights) and DP (Data Parallel — split batches), TT-Metal supports Pipeline Parallelism:

  • How it works: Model layers are split across chips. Chip 0 runs layers 0-7, chip 1 runs layers 8-15, etc. Activations flow chip-to-chip via Ethernet as a pipeline — while chip 0 processes batch N+1, chip 1 processes batch N.
  • When to use: Models too large for single-chip TP (weights exceed DRAM). Combines with TP for optimal scaling: TP within layers, PP across layers.
  • PP + TP + DP: Full 3D parallelism — TP splits layers within a node, PP splits layers across nodes, DP replicates across node groups. Used for largest training workloads.
  • Implementation: Handled by TT-Fabric and TT-Distributed. Tech reports: "TT-Fabric Architecture," "TT-Distributed Architecture."

14. Limitations & Known Issues

14.1. IEEE 754 Compliance

TT hardware is NOT fully IEEE 754 compliant. Only select FPU ops (add_tiles, mul_tiles, matmul_tiles) and SFPU ops handle Inf/NaN per IEEE. All other operations treat special numbers as ordinary values with undefined results. Denormals are flushed to zero in ALL formats. Special values are only detected at FPU/SFPU output — intermediate Inf/NaN may go undetected. Detection is per-core OR'd across lanes — you cannot tell which lane produced the special value.

14.2. Hardware Constraints

  • Fixed 32×32 tile size — all tensors padded to tile boundaries. Wasted memory for non-aligned dimensions.
  • 5 RISC-V CPUs per Tensix core — 32-bit RV32IM, no FPU on baby RISC-V. They dispatch, not compute.
  • 1.5 MB SRAM per core — large models must spill to DRAM (higher latency).
  • Matrix engine minimum dimensions — 8×16 for in0, 16×16 for in1. Smaller dims waste compute (1/8 throughput for 1×16).
  • No automatic caching — all memory movement is explicit via circular buffers and NoC.
  • No built-in threadIdx — explicit per-core runtime args required for SPMD.

14.3. Known Gaps

  • 40+ experimental models still in bring-up (DeepSeek-V3, Grok, Falcon-40B, Mistral-24B, SDXL, VAE, YOLO, DETR3D, EfficientDet, SwinV2, InceptionV4, DeIT, BLIP, gemma4, NanoGPT, BGE, etc.)
  • Blackhole optimization is under active development — many models not yet supported on BH
  • from_torch with ROW_MAJOR_LAYOUT hangs on certain 5D tensor shapes with permute (known bug on BH)
  • No integer quantization — no int8 or int4 support, only block floating-point
  • Training less mature than inference — TT-Train exists (111K lines) but with fewer models and optimizers than inference
  • Linux only — no Windows or macOS support
  • Limited third-party ecosystem — vLLM plugin exists but no native ONNX Runtime, TensorRT, or OpenVINO integration

14.5. Custom TT-NN Operator Development

When an operation you need doesn't exist in TT-NN, you write it yourself at the Metalium level:

  1. Write the kernels: You need 3 kernels — reader (DRAM→CB), compute (math on tiles), writer (CB→DRAM). See Metalium section 4 for full kernel examples.
  2. Create the TT-NN wrapper: Write a Python function that: creates the program, allocates CBs, compiles kernels, sets runtime args, enqueues work, reads results.
  3. Register in the right category: Place your op in the matching ttnn/cpp/ttnn/operations/ category (eltwise, matmul, data_movement, etc.).
  4. Add Python bindings: Expose via nanobind so it's callable from Python as ttnn.my_custom_op().
  5. Test: Run 1 core, 1 tile, BF16 — compare against PyTorch reference. Then scale up.

Full guide: "Op Kernel Development" tech report in tech_reports/. Existing ops in ttnn/cpp/ttnn/operations/ (33 categories) are the best reference implementations.

14.6. Dynamic Shapes & Variable-Length Sequences

TT hardware does not natively support dynamic shapes. The 32x32 tile is fixed. Every tensor dimension is known at compile time. Changing a tensor shape requires re-compiling the program.

Workarounds:

  • Pre-allocation: Models pre-allocate maximum context length buffers and use masking. A model supporting up to 128K context pre-allocates for 128K even when using 1K.
  • KV Cache: TT-NN has dedicated KV cache operations (in the kv_cache op category) that handle variable-length sequences efficiently — cache grows as tokens are generated.
  • Padding: Short sequences are padded to the next 32-multiple. The hardware's pack/unpack engines handle padding at zero cost.
  • Batching: Different sequence lengths in a batch require padding all to the longest. Use attention masks to ignore padding tokens.

For truly dynamic workloads (variable batch sizes, changing model architectures), consider using TT-Forge or TT-XLA which handle shape polymorphism at the compiler level.

16. Error Handling & Debugging Guide

16.1. What Happens When a Kernel Crashes

When a RISC-V kernel faults (e.g., out-of-bounds memory access, illegal instruction):

  1. Watcher (firmware monitor) detects the hang/fault within seconds
  2. The faulting core's state is captured: program counter, register dump, last instructions
  3. DPRINT buffer (if enabled) contains any debug messages the kernel printed before crashing
  4. The host receives a waypoint/error code indicating which core failed and what type of fault
  5. The command queue enters error state — subsequent commands are rejected until device reset

15.3. Security Architecture — RISC-V Sandbox

Understanding the isolation model helps identify where boundaries can be broken:

Hardware isolation properties:

  • Per-core SRAM isolation: Each Tensix core's 1.5 MB SRAM is physically separate. One core cannot access another core's SRAM without an explicit NoC transaction. No cache coherency means no speculative side channels.
  • No MMU on baby RISC-V: The 5 RISC-V CPUs per core are RV32IM (Machine mode only) — no virtual memory, no page tables, no user/supervisor separation. Kernel code runs bare-metal.
  • No OS on device cores: Kernels are compiled C++ running bare-metal on RISC-V. There is no process isolation between kernels on the same core — a kernel has full access to its core's SRAM.
  • Dispatch via command queue: The host queues commands. The device's dispatch RISC-V core processes them. No direct host access to device SRAM.
  • No speculative execution: RISC-V RV32IM cores are simple in-order processors — no Spectre-class side channels.

What isolation does NOT exist:

  • A malicious kernel on one core can issue NoC reads/writes to any other core's SRAM or any DRAM bank
  • The NoC does not enforce access control — any core can read/write any address reachable via NoC
  • Kernels are compiled from user-provided C++ — the JIT compilation path is a code injection surface
  • Python bindings (nanobind) cross the host C++/Python boundary — type confusion and refcounting bugs possible
Model isolation: Running untrusted third-party models provides limited isolation. A malicious kernel can read other models' weights if co-located and disrupt other workloads by corrupting shared DRAM. Do not co-locate untrusted models with sensitive workloads on the same chip.

15.4. How to File a Good Bug Report

For issues on github.com/tenstorrent/tt-metal/issues:

  1. Environment: tt-metal version, firmware version (tt-smi -l | head -3), device type, OS, Python version
